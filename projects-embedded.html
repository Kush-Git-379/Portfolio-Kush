GF(2⁸) Arithmetic Core in Verilog, Verified Exhaustively

I wrote a Reed–Solomon erasure decoder in C++ at ISRO, then wanted to know what the arithmetic underneath it looks like in hardware. This is that: gf_mul, gf_inv and gf_mac as synthesizable RTL, checked against the original C++ as golden reference. It is the arithmetic layer a decoder sits on, not the decoder itself. Two multiplier microarchitectures went in so I could compare them, and the comparison turned out to be the interesting part.

The Result I Did Not Expect

  • Textbook advice is that log/antilog tables beat shift-and-reduce, because a table lookup is cheaper than a loop. On this FPGA the opposite held: the table version came out 13× larger and 1.7× slower
  • The cause was asynchronous ROM reads. Without a registered read address Quartus cannot infer M9K block memory, so it built 768 bytes of table out of logic elements instead, and the read path picked up an address decode, a 256-entry mux, a 9-bit add and a 512-entry mux
  • The shipped core therefore uses combinational shift-and-reduce at 62 LEs and 129.6 MHz
  • The transferable lesson: log/antilog is right on a CPU, where the table sits in cache and the alternative is a genuine loop. On fabric without registered-read memory, shift-and-reduce wins on area and timing at once. That is measurable, not arguable

Verification

  • Golden vectors generated from the C++ decoder I wrote at ISRO, so the reference is an implementation that already worked against real satellite data
  • Multiply is checked over every input pair, all 65,536 of them. At 2¹⁶ combinations a complete proof is achievable, so sampling would have been the weaker claim
  • Inverse covers all 256 cases including the zero-input error path; MAC accumulates 1,180,160 checks
  • Three seeded faults were injected to confirm the benches actually fail when the design is wrong. A green run from a test that cannot fail is evidence of nothing
  • Synthesis reports zero inferred latches across all modules

Summer Internship SAC · ISRO Navigation Receiver Division May – Jul 2026 · 10 Weeks

Development of a Real-Time HAS (High Accuracy Service) Decoding Utility, SAC, ISRO

Ten weeks at ISRO's Space Applications Centre, in the division that builds GNSS and NavIC receivers. The project was a real-time, multi-protocol decoding utility that ingests a multiplexed stream from a network socket carrying three interleaved components: raw RTCM hex payloads, Galileo HAS pages from the E6-B signal, and Time-of-Transfer epoch metadata. The utility tokenizes and routes each component down its own pipeline; native RTCM is converted from hex back to binary and forwarded directly, while HAS pages are reassembled and passed through a Reed–Solomon erasure decoder over GF(256) to recover Precise Point Positioning corrections, which are then re-encoded as standard RTCM 3.x messages on an independent output port. Built in C and then C++ under a pre-C++11 compiler constraint, and validated end-to-end in RTKLIB's RTKNAVI to achieve centimetre-level positioning.

Engineering Highlights

  • Implemented Galois Field GF(256) arithmetic from first principles: log/exp lookup tables, XOR addition, and Gaussian elimination for k×k matrix inversion, material outside the undergraduate syllabus
  • Reed–Solomon erasure decoding recovers a complete HAS message from any MS valid pages out of 255, tolerating page loss and out-of-order arrival
  • Reverse-engineered the Galileo RTCM messages 1240–1243 and the CRC-24Q routine, which were absent from the RTCM manual available at the time, by cross-referencing the HASlib source against the Galileo HAS ICD
  • Dual-egress architecture: native RTCM to Port A, HAS-decoded RTCM to Port B, with TOT metadata anchoring both pipelines to the correct satellite clock epoch
  • Timestamp-based stale-page purging discards buffered pages after 150 s without completing a message
  • Worked around a pre-C++11 Dev-C++ / MinGW toolchain using fixed-array data structures and Win32 CreateThread for concurrency
  • Validated at two levels; per-stage unit comparison against a Python reference utility, then end-to-end with RTKNAVI consuming the live correction stream over localhost

Simulation & Comparison of Cryptography Algorithms for Lightweight Embedded Systems

Four ciphers, one question: which of these can a sensor node actually afford to run? I benchmarked DES, AES-GCM, ASCON and ECC under identical conditions. Each algorithm was benchmarked across total execution time and per-operation latency on identical hardware. ASCON, the NIST-selected lightweight cryptography standard, demonstrated a 78× speed advantage over AES-GCM and a 12× advantage over DES, directly validating its design intent for IoT edge devices. ECC was evaluated separately as an asymmetric key exchange primitive.

Key Findings

  • ASCON achieved 0.0032 ms per operation, 78× faster than AES-GCM and 12× faster than DES
  • AES-GCM's authenticated encryption overhead is the dominant cost on constrained hardware, making it unsuitable for high-frequency IoT sensor data
  • ECC provides efficient asymmetric key exchange at 8.45 ms per handshake: viable for session establishment but not per-message encryption
  • Results directly motivated the follow-up ESP32 hardware implementation to validate simulation findings on real constrained hardware

Secure GPS Location Tracker, ESP32 + AES-128 + MQTT + Google Maps

A GPS tracker where the location never travels in the clear. An ESP32 reads GPS coordinates via TinyGPS++ over UART2, serializes them to JSON, encrypts with AES-128 (mbedTLS), and publishes the hex ciphertext over MQTT. A Python subscriber decrypts each message and automatically opens the live location in Google Maps. Validated at Nirma University (23°07'44.5"N, 72°32'31.9"E); confirming correct GPS acquisition, encryption, MQTT transport, and decryption across the full pipeline.

System Pipeline

  • GPS module on UART2 (GPIO 16/17) → TinyGPS++ parses NMEA sentences → JSON payload: {"lat":23.129021,"lon":72.542191}
  • AES-128 ECB encryption via mbedTLS (built into ESP32 SDK), zero-padded to 16-byte boundary, hex-encoded output
  • MQTT publish to kush/esp32/gps_encrypted on HiveMQ broker every 3 seconds
  • Python subscriber: AES decrypt → JSON parse → webbrowser.open(google.com/maps?q=lat,lon)
  • Verified: Serial monitor confirmed GPS fix, Mosquitto terminal showed continuous encrypted hex stream, browser opened correct Nirma University location

A surveillance system that runs the whole chain itself: camera to detection to database to dashboard, with nothing rented from a cloud vendor except optional telemetry. A Raspberry Pi 3B captures over the CSI bus, detects motion, streams MJPEG over authenticated HTTP, logs sessions to SQLite, and serves a live Flask dashboard. The interesting part was finding out what a Pi 3 will and will not do. Built with Vasu Mistry, Nabh Sinha and Parth Kothari.

What the Pi Could and Couldn't Do

  • Exported YOLOv8n to ONNX (12.7 MB) and loaded it on the Pi through cv2.dnn.readNetFromONNX. The model ran, but inference was slow enough to stall the MJPEG stream, so deep learning stayed on the laptop
  • Replaced it with MOG2 background subtraction, which holds 8 to 15 FPS on the same hardware: history 300 frames, varThreshold 40, 5×5 elliptical opening, contours above 3,000 px counted as motion
  • The conclusion is the useful bit. A Pi 3 is a capable capture and streaming node, but real-time CNN inference needs either a Pi 4/5 or an accelerator like a Coral USB stick
  • Session tracking with a 4-second gap timeout, so one person walking past logs as one session rather than forty
  • MJPEG over multipart/x-mixed-replace with HTTP Basic Auth; failed attempts logged to a viewer_log table with client IP
  • Three-table SQLite schema (sessions, telemetry, viewer_log) and a seven-endpoint Flask REST API feeding a Chart.js dashboard that refreshes every 5 seconds
  • Anedya cloud telemetry was wired up but the demo network had no internet, so it failed over to local-only logging and lost nothing

Computer Architecturegem53EC503CC24 · Nirma University · 2026

L1 Cache Sensitivity Analysis: Matrix Multiplication vs AES Encryption using gem5

Microarchitectural simulation study using gem5 v25.1 on an X86 TimingSimpleCPU, comparing cache sensitivity across two fundamentally different workloads: a 100×100 matrix multiplication (~40kB working set, memory-intensive) and an AES SubBytes encryption benchmark (150kB payload, non-linear S-Box lookups). Three experiments were conducted, varying cache capacity (4kB→64kB) on each workload, and varying associativity (1-way→8-way) at fixed 16kB. The key finding is that cache optimization is strictly workload-dependent: matrix multiplication responds dramatically to both capacity and associativity, while AES is almost entirely insensitive to cache scaling.

Key Conclusions

  • Matrix multiplication is highly cache-sensitive: miss rate drops 99% (5.06%→0.04%) as cache grows large enough to hold the ~40kB working set
  • AES SubBytes is cache-insensitive: the 256-byte S-Box fits even in a 4kB cache, so the bottleneck lies in instruction execution, not memory capacity
  • At constrained 16kB, conflict misses dominate matrix multiply, 8-Way associativity reduces miss rate from 4.74% to 0.34% and improves IPC by 10.4%
  • Practical recommendation for UAV flight controllers and IoT edge nodes: use highly-associative but modestly-sized caches; 8-Way at 16kB outperforms direct-mapped at the same size while avoiding the area and power cost of larger caches

FPGADigital Design2EC202 · Nirma University

FPGA Digital Design, Wallace Tree Multiplier & Fastest Finger First Game

Two digital design projects implemented on FPGA using Verilog HDL. The Wallace Tree Multiplier implements an 8×8 bit parallel multiplier producing a 16-bit output, reducing partial product addition to O(log n) stages using carry-save adder trees, significantly lower propagation delay than conventional O(n) array multipliers. The Fastest Finger First (FFF) buzzer system detects the first button press among multiple players with microsecond precision using finite state machines and hardware debounce logic. Both designs were fully verified with ModelSim testbenches before FPGA synthesis and timing closure in Quartus Prime.

Design Details

  • Wallace Tree: three-stage pipeline: partial product generation (AND gates), tree reduction (HA/FA carry-save adders), final carry-propagate addition
  • 8×8 implementation produces all 64 partial products then reduces column-by-column; result[7] alone requires six full adders and one half adder in sequence
  • Simulation confirmed correct output in ModelSim (e.g., 10 × 11 = 110 decimal validated in waveform); RTL and TTL synthesis views confirmed tree structure
  • FFF game: FSM-based priority encoder with hardware debounce, first-press latency bounded by clock period, not software polling loop
  • Timing closure achieved post place-and-route in Quartus Prime; no setup/hold violations

DevOps · ScriptingLinux3EC504ME24 · Nirma University · 2026

Log Analytics and Anomaly Detection Tool

A small monitoring tool in two halves, each written in the language that suited it. The Bash module (collector.sh) interfaces directly with Linux kernel utilities (top, free, df) via command substitution and pipelines, extracting CPU, memory, disk, and failed login metrics into a timestamped CSV, scheduled via cron for fully automated collection. The Python module (detector.py) parses the CSV with pandas, computes a statistical baseline (µ and σ) from historical data, and raises anomaly alerts when readings breach the dynamic µ+2σ threshold, dispatching automated email alerts via smtplib. Validated by CPU stress-testing with background loop processes that successfully triggered the threshold breach and alert pipeline.

System Design

  • Two-module architecture: Bash handles kernel-level data extraction; Python handles statistical analysis and alerting: each language used for its strengths
  • Dynamic µ+2σ threshold computed from historical baseline, adapts to the system's normal operating conditions rather than using fixed thresholds
  • Metrics collected: CPU usage (via top pipeline), memory (free), disk utilisation (df), and failed SSH login attempts
  • Validated under stress test: background yes > /dev/null loop processes successfully breached threshold and triggered email alert
  • Known limitation: cold start problem; µ+2σ becomes accurate only after sufficient baseline data is collected; early runs may yield false positives

Review PaperIoT · CommunicationsB.Tech ECE · Nirma University

Applications of Digital Communication in IoT, Survey & Smart Agriculture Case Study

A survey of the wireless technologies IoT deployments actually choose between, with smart agriculture as the worked example. The paper classifies IoT wireless technologies into three tiers, short-range (BLE, Zigbee, Wi-Fi), medium-range (LTE, 5G), and long-range LPWANs (LoRaWAN, Sigfox): and analyses each as a deliberate trade-off among the IoT design triangle of range, data rate, and battery life. Communication fundamentals covered include Shannon-Hartley capacity, CSS and GFSK modulation, FEC coding, DSSS/FHSS spread spectrum, and ALOHA vs CSMA/CA channel access for dense IoT deployments.

Key Technical Content

  • LoRaWAN with Chirp Spread Spectrum (CSS) identified as dominant choice for remote field sensors, CSS decodes signals even at negative SNR
  • Non-Terrestrial Networks (NTN): satellite backhaul and UAV drones as mobile data collectors bridge connectivity gaps in areas without terrestrial coverage
  • Three-tier data processing hierarchy: edge devices (real-time actuation) → fog gateways (local filtering) → cloud (long-term predictive analytics)
  • MQTT highlighted as preferred application-layer transport for its lightweight pub-sub footprint; connects directly to ESP32 MQTT project
  • Future trends: RF energy harvesting targeting 15–20 year sensor lifetimes, Reconfigurable Intelligent Surfaces (RIS) for terrain-blocked rural deployments
  • Security analysis across perception, network, and application layers, DoS, eavesdropping, and data injection attack vectors
